# 트러블슈팅

fake 모델로만 돌릴 때는 드러나지 않던 장애를 **일부러 일으켜서** 확인하고 고친 기록이다.
항목마다 `재현 → 증상(수정 전 실제 출력) → 원인 → 수정 → 확인(수정 후 같은 스크립트 출력)` 순서로 적었다.
가설이 틀린 부분도 그대로 남겼다(⑦).

## 재현 환경

실제 Ollama 대신 **모의 Ollama**(`tests/repro/mock_ollama.py`, 포트 11999)를 띄우고 Re-cat을 `LLM_BACKEND=ollama`로 붙였다.
모의 서버는 `tests/repro/mode.json`으로 동작을 바꾼다(재시작 없이).

| mode                  | 동작                                                                          |
| --------------------- | ----------------------------------------------------------------------------- |
| `{"delay": 5}`        | 매 응답 5초 지연                                                              |
| `{"fail": N}`         | 앞으로 N번 HTTP 503(모델 로딩 중)                                             |
| `{"bad_json": true}`  | 설명 응답 JSON이 중간에 잘림                                                  |
| `{"fake_name": true}` | 설명 본문에만 없는 함수 이름(`AuditLogger.write`)을 쓰고 claims에는 넣지 않음 |

```bash
bash tests/repro/up.sh                     # 모의 Ollama + Re-cat 기동 (RECAT_MCP_TIMEOUT=5 를 앞에 붙이면 ②가 빨리 끝남)

```

회귀 테스트: `pytest tests/test_resilience.py tests/test_doc_questions.py` (위 상황을 코드로 일으켜 확인)

## ① 느린 모델 호출이 서버 전체를 멈춤

**재현** 모델 응답을 5초로 늦추고(`{"delay": 5}`), 질문 하나를 보낸 1초 뒤 `/health`를 3번 호출.

**증상(수정 전)**

```
  /health 4.062212s      ← 진행 중인 모델 호출이 끝날 때까지 대기
  /health 0.001415s
  /health 0.001438s
  질문: 200 25.42s
```

**원인** `ollama_llm.py`·`openai_llm.py`가 `async def` 안에서 동기 `httpx.post(timeout=180)`을 불렀다.
그 사이 이벤트 루프가 멈춰 다른 사용자의 질문·관리자 화면·헬스체크가 모두 기다렸다.
라우팅·탐색 선택(`route`, `select_expansions`)은 동기 함수를 그래프 노드에서 그대로 불렀다.

**수정** 모델 호출을 `asyncio.to_thread`로 감쌌다(어댑터의 `explain`·`chat`·`explain_doc`, 그래프의 `route`·`select_expansions`).

**확인(수정 후)**

```
  /health 0.001245s
  /health 0.001063s
  /health 0.000897s
```

회귀 테스트 `test_slow_llm_call_does_not_block_event_loop`: 1초 걸리는 모델 호출 동안 0.05초 주기 태스크의 최대 간격 < 0.3초.

## ② MCP 서브프로세스가 멈추거나 죽으면 복구되지 않음

**재현** 질문 직전에 MCP 서브프로세스(`mcp_server.py`)를 `SIGSTOP`(멈춤) / `SIGKILL`(죽음).

**증상(수정 전)**

```
  MCP → SIGSTOP(멈춤)
  000 20.002s                      ← 응답 없음, 클라이언트 20초 제한에 걸림
  MCP → SIGKILL(죽음)
  500 0.06s  Internal Server Error
  5초 뒤 다시:
  500 0.06s  Internal Server Error  ← 서버를 재시작할 때까지 계속
  (서버 로그) mcp.shared.exceptions.MCPError: Connection closed
```

**원인** 두 가지가 겹쳤다.

1. MCP 호출에 시간 제한이 없었다. `with_retry`는 `asyncio.TimeoutError`만 재시도하는데, 시간 제한이 없으니 그 예외가 날 일이 없었다 — **재시도 로직이 데모용 시뮬레이션(`RECAT_FLAKY`)에서만 동작하고 있었다.**
2. 연결이 끊기면 다시 연결하는 코드가 없었다. 서브프로세스는 서버 기동 때 한 번만 띄웠다.

**수정** (`agent/mcp_client.py`, `agent/retry.py`)

- 모든 MCP 호출에 시간 제한: `RECAT_MCP_TIMEOUT`(기본 60초). 저장소를 처음 분석할 수 있는 관리자 도구(`reanalyze`, `get_status`)는 600초.
- 시간 초과·연결 끊김이면 서브프로세스를 **다시 띄우고** `TransientError`를 올린다 → `with_retry`가 재시도한다.
- 여러 요청이 동시에 실패해도 재시작은 한 번만(세대 번호 비교).
- 연결은 전용 태스크가 연다·닫는다. anyio 컨텍스트는 연 태스크에서 닫아야 해서, 요청 태스크에서 닫으면 오류가 난다.
- 도구 자체의 오류(잘못된 함수 이름 등)는 재시작·재시도하지 않는다.

**확인(수정 후, `RECAT_MCP_TIMEOUT=5`)**

```
  MCP pid=1012 → SIGSTOP(멈춤)
  200 11.37s   mode=agent ok=True verified=5
  MCP pid=1032 → SIGKILL(죽음)        ← 새 프로세스로 바뀌어 있음
  200 2.06s    mode=agent ok=True verified=5
  (서버 로그) MCP 서브프로세스 재시작: list_functions: TimeoutError
             MCP 서브프로세스 재시작: list_functions: MCPError
```

회귀 테스트 `test_mcp_client_recovers_from_killed_and_frozen_subprocess`.

## ③ 모델이 503(로딩 중)을 주면 질문 전체가 실패

**재현** `{"fail": 2}` — 다음 두 번의 모델 호출이 503.

**증상(수정 전)** `500 0.08s Internal Server Error`

**원인** 모델 HTTP 호출에 재시도가 없었고, 모델 호출 실패를 그래프가 받아 주지 않았다.
정적 분석 결과는 이미 다 있는데도 답을 못 했다.

**수정**

- `llm_common.post_json`: 연결 실패·시간 초과·408/429/5xx만 지수 백오프로 3회 재시도(0.5초 → 1.5초). 4xx는 즉시 실패.
- 그래도 안 되면 `LLMUnavailable` → 단계별 대체 경로:

| 단계              | 대체                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------- |
| route             | 규칙 기반 분류(fake 라우터의 정규식)                                                        |
| select_expansions | 후보 전부 열기                                                                              |
| explain           | **fallback 노드 → 정적 분석 결과만으로 답변** (`[해석 없음 — 모델 서버가 응답하지 않아 …]`) |
| doc_explain       | 문서–코드 대조 결과(결정적)만 제공                                                          |
| chat              | 안내 문장                                                                                   |

**확인(수정 후)**

```
③  503 두 번:      200 2.50s  mode=agent ok=True verified=5         ← 재시도로 복구
③-b 계속 503:      200 10.85s mode=no-llm-fallback
    이벤트: LLMUnavailable(route) → RouteDecided → … → LLMUnavailable(explain) → Fallback → Finalize
```

## ④ 스트리밍 중 오류가 나면 아무 기록 없이 끊김

**재현** ③과 같은 상황을 `/chat/stream`으로.

**증상(수정 전)**

```
  data: {"type": "GateDecided", ...}
  (끝 — FinalAnswer도 [DONE]도 없음)
  감사 로그: chat_stream 기록 없음
```

화면에는 "연결이 끊겼습니다. 서버 상태와 API 키를 확인하세요."만 뜬다 — 원인과 상관없는 안내.

**원인** `chat_stream`의 `astream` 루프에 예외 처리가 없었다. `/chat`도 원인 없는 500만 돌려줬다.

**수정** 예외를 잡아 `{"type": "Error", "message": …}` 이벤트와 `[DONE]`을 보내고 감사 로그에 `chat_error`(예외 종류만, 내용 없음)를 남긴다.
`/chat`은 503과 이유 문장. 화면은 `Error` 이벤트를 받아 그 문장을 보여 준다.

**확인** ③이 고쳐져 같은 상황에서는 이제 오류가 나지 않는다(`FinalAnswer` → `[DONE]`, 감사 로그 `chat_stream`).
예외 경로는 회귀 테스트 `test_unexpected_error_is_reported_not_dropped`로 강제로 일으켜 확인.

## ⑤ 모델이 깨진 JSON을 주면 "검증 통과"로 집계됨

**재현** `{"bad_json": true}`

**증상(수정 전)** `200 mode=agent attempts=1 ok=True verified=0` — 설명은 비었는데 "구조 검증 통과" 배지.

**원인** 어댑터가 JSON 파싱 실패를 `{}`로 바꾸고 → claims가 빈 목록 → 오류 주장 0개 → `ok=True`.
**평가 지표(검증 통과율)가 부풀려지는 데이터 정합성 문제**였다.

**수정** `verify(..., text=설명, require_claims=호출 구조가 있는가)`: 설명이 비었거나, 호출이 있는데 주장이 하나도 없으면 `empty=True`, `ok=False` → 재설명 → 끝내 안 되면 fallback.
문서 경로는 주장이 없는 게 정상일 수 있어 적용하지 않는다.

**확인(수정 후)** `mode=no-llm-fallback attempts=3 ok=False verified=0`

## ⑥ 설명 본문에만 쓴 가짜 함수가 검증을 빠져나감

**재현** `{"fake_name": true}` — 본문에 "AuditLogger.write로 감사 로그를 남깁니다", claims에는 없음.

**증상(수정 전)** `ok=True verified=5 halluc=0`, 사용자 화면에 `AuditLogger.write`가 그대로 보임.

**원인** 검증기는 **LLM이 스스로 신고한 claims만** 대조했다. 본문과 claims가 따로 놀아도 몰랐다.

**수정** 본문에서 코드 이름을 규칙으로 뽑아(`` `백틱` ``, `A.b` 꼴) 저장소에 없으면 hallucinated(호출자 `(설명 본문)`)로 센다.
오탐을 줄이려고 파일 이름(`service.py`), `self.`·`this.` 경유, 소문자로 시작하는 인스턴스 변수 경유(`stock.decrease` — 메서드 이름만 확인)는 제외했다.

**확인(수정 후)** `mode=no-llm-fallback attempts=3 ok=False verified=5 halluc=1`

**한계** 이름을 백틱이나 점 표기 없이 자연어로만 쓰면("감사 로거에 기록") 잡지 못한다.

## ⑦ 관리자 업로드 동시 요청 — 가설 일부는 틀렸고, 더 나쁜 문제가 나왔다

**처음 가설** `registry.json`을 읽고 고쳐 쓰는 사이에 잠금이 없어, 동시 등록이면 한쪽이 사라진다.

**재현 1 — 다른 이름 5개 동시** → `200 ×5`, 폴더 5개, 등록 5개. **재현되지 않음.**
등록 함수는 중간에 `await`가 없는 동기 코드라 서버 프로세스 하나 안에서는 끼어들 틈이 없다. 가설이 틀렸다.

**재현 2 — 같은 이름에 서로 다른 zip(v1 함수 7개 / v2 함수 8개) 동시** (6회)

```
  시도2: v1요청=400 v2요청=200 | 성공 응답=v2, 디스크 파일=v1, 분석 함수 수=[7]  ← 불일치
  시도4: v1요청=200 v2요청=400 | 성공 응답=v1, 디스크 파일=v2, 분석 함수 수=[8]  ← 불일치
  시도5: v1요청=200 v2요청=400 | 성공 응답=v1, 디스크 파일=v2, 분석 함수 수=[8]  ← 불일치
```

**6번 중 3번, "실패(400)"를 받은 요청의 파일이 디스크에 남았다.** 관리자 화면은 성공한 쪽 버전이라고 보여 주는데 실제 분석은 다른 버전 — 데이터 정합성 문제.

**원인** `extract_repo`는 처음에 "같은 이름이 있나"를 확인하고 압축을 푼 뒤, 마지막에 `if dest.exists(): 교체`를 했다.
이 마지막 분기가 `replace` 여부를 보지 않아, 압축을 푸는 사이 다른 요청이 먼저 설치하면 **새 업로드인데도 덮어썼다.** 그 뒤 등록 단계에서 "이미 등록됨"으로 400을 돌려줬다.

**수정**

- `extract_repo`: 마지막 단계에서도 `replace`가 아니면 거절(덮어쓰지 않음).
- 관리자 쓰기 API(등록·업로드·문서·재분석)를 `asyncio.Lock`으로 한 번에 하나씩 처리.
- `registry.json` 임시 파일 이름을 요청마다 다르게(`mkstemp`).

**확인(수정 후)** 6번 모두 `성공 응답 = 디스크 파일 = 분석 함수 수`.

**곁가지 발견** `registry.json`을 지워도 서버 메모리의 허용 목록에는 남는다(저장소 삭제 기능이 없어서 설계상 '더하기만' 한다). 재현 스크립트를 처음 짤 때 이것 때문에 두 요청이 모두 400이 나와 시도마다 새 이름을 쓰도록 바꿨다.

## ⑧ 교체 업로드 도중 실패하면 저장소가 사라짐

**재현** 교체 중 "기존 폴더를 치운 직후, 새 폴더를 제자리로 옮기는 순간" 디스크 오류(ENOSPC)를 일으킴.

**증상(수정 전)**

```
  교체 전: ['shop']
  교체 중 오류: [Errno 28] No space left on device
  교체 후: ['.replaced-shop'] / shop 폴더 있음: False
```

**원인** `dest → .replaced-이름`으로 옮긴 뒤 `tmp → dest`가 실패하면 되돌리는 코드가 없었다.

**수정** `tmp → dest` 실패 시 `.replaced-이름 → dest`로 되돌리고 예외를 올린다.

**확인(수정 후)** `교체 후: ['shop'] / shop 폴더 있음: True`

## ⑨ 없는 함수를 물으면 비슷한 함수의 흐름으로 대신 답함

**발견** 문서 질문을 시험하다가 대조군으로 넣은 질문에서 나왔다.

**증상(수정 전)**

```
Q: PaymentGateway.charge 흐름          (저장소에 없는 이름)
route=trace mode=agent
'PaymentClient._post는 정적 분석으로 확인되는 다른 함수 호출이 없어요.'
```

검증은 통과한다 — 답한 호출 관계 자체는 사실이기 때문이다. 하지만 **질문과 다른 함수에 대한 답**이라 사용자는 `PaymentGateway.charge`가 있다고 믿게 된다. 시스템이 만드는 환각이다.

**원인** 시작 함수 검색이 이름 일치(10점·6점) 외에 토큰 겹침(0.5점씩)도 점수로 쳐서, "Payment" 토큰만 겹쳐도 가장 높은 함수를 골랐다.

**수정** 질문에 `A.b` 꼴 코드 이름이 있는데 저장소에 그 이름(정규 이름·짧은 이름)이 없으면 탐색하지 않고 "없는 이름입니다. 비슷한 이름: …"으로 답한다. 이름 없이 기능으로 묻는 질문("주문 생성은 어떻게 동작해?")은 그대로 검색한다.

**확인(수정 후)** `PaymentGateway.charge은(는) 이 저장소에 없는 이름입니다. 비슷한 이름: PaymentClient._post, PaymentClient.refund, PaymentClient.request`
회귀 테스트 `tests/test_doc_questions.py`.

**같이 고친 것 — 문서 내용 질문** `TROUBLESHOOTING.md`를 문서로 올리고 물어보니, "문서에서 …"라고 물으면 맞는 절을 찾았지만
"트러블슈팅에서 MCP가 죽으면?"은 코드 질문으로 분류돼 "시작 함수를 찾지 못했습니다", "남은 한계가 뭐야?"는 잡담으로 분류돼 인사말이 나왔다.
이제 코드 질문인데 시작 함수가 없거나, 잡담으로 분류됐는데 등록 문서와 충분히(점수 3 이상) 겹치면 문서 질문으로 처리한다.
문서 답변은 원문을 붙이는 대신 설명이 문서 내용으로 먼저 답하고, 원문은 "근거 보기"로 접힌다.

## ⑩ 실제 Ollama 첫 실행에서 Re-cat 경로가 한 문항도 설명까지 가지 못함

**재현** 실제 Ollama(qwen3:0.6b 분류 / qwen3:8b 설명, MacBook Pro)로 `python -m eval.run_eval --limit 4`.

**증상**

```
[1/4] sample_py:OrderService.create  A=1/4 B=- C=-
...
A 코드만 준 LLM   주장 12  오류율 41.7%  오류 있는 질문 3/4
B·C               주장 0
진입점 적중률 0%
```

A(코드만 준 LLM)는 정상 동작했고 — **실제 모델이 호출 관계 주장의 41.7%를 틀렸다** — Re-cat(B·C)만 시작 함수를 고르기 전에 빠졌다.

**원인(추정)** 질문 분류를 0.6B 모델에 전부 맡겼다. 코드 질문을 '잡담'(또는 '문서')으로 분류하면 시작 함수 탐색 자체를 하지 않는다.
fake 모델은 정규식이라 항상 맞게 분류해서 드러나지 않았다. 이 실행은 수정 전 코드라 분류 결과가 기록되지 않아 **확정은 다음 실행에서** 한다(아래 기록 추가).

**수정**

- 규칙이 먼저 분류한다: 코드 이름이나 '호출·흐름·동작·어떻게·무엇을' → 코드 질문, '문서·명세·기획서·N단계' → 문서 질문. 규칙이 '잡담'으로 본 애매한 질문만 모델에 묻는다. 작은 모델의 실수가 핵심 경로를 막지 못하고, 모델 호출도 줄어든다.
- 실험 결과에 문항별 `route`·`mode`를 기록하고 출력한다(`· 분류=trace 시작=OrderService.create`). B·C가 비면 왜 비었는지 바로 보인다.
- `VERSION` 파일과 실험 첫 줄의 `Re-cat 버전`으로 받은 코드가 최신인지 확인한다(이 실행이 예전 zip이었다는 걸 늦게 알았다).

**확인** 모의 Ollama가 모든 질문에 '잡담'이라고 답하게 해도 코드 질문은 `분류=trace(rule)`로 시작 함수까지 간다. 회귀 테스트 `test_rules_route_code_questions_even_if_model_says_chat`.

## 남은 한계 (고치지 않음, 알고 있음)

- **모델이 완전히 죽었을 때 응답이 느리다**(③-b 10.9초). 호출마다 3회 재시도를 반복한다. 일정 시간 연속 실패하면 바로 대체 경로로 가는 차단기(circuit breaker)가 다음 단계.
- **관리자 잠금은 서버 프로세스 1개 기준**이다. 여러 워커(`uvicorn --workers N`)로 띄우면 파일 잠금이 필요하다.
- **교체 후 재분석이 실패하면** 파일은 새 버전, 분석 캐시는 비어 있는 상태가 된다(다음 질문 때 다시 분석). 이전 버전으로 되돌리지는 않는다.
- **MCP 호출은 잠금 하나로 직렬 처리**된다. 동시 사용자가 많으면 느려진다.
- 문서 질문은 **가장 잘 맞는 절 하나**로만 답한다. 여러 절을 묶어야 하는 질문("문서 전체 요약")은 약하다.
- 실제 Ollama 모델이 아닌 **모의 서버로 확인**했다. 실제 모델의 응답 형식·속도는 별도로 확인해야 한다.
